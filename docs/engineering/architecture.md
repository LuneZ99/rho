# 技术架构

## 已确定的选型

- React Native + Expo + TypeScript。
- 当前目标平台以 [产品需求](../product.md) 为准。
- 采用远程 Agent 与共享工作环境，服务端保存业务主记录，手机提供设备能力和离线副本；部署地点见 [运行位置决策](agent-runtime-decision.md)。首个 demo 已开始实现和 Compose 部署；具体组件、接口、运行状态与限制见[首个 demo 技术说明](demo.md)。

## 待验证事项

以下为用户提出的技术方向，尚未完成可行性验证，不代表已有可运行方案。

用户已明确多个对话共用服务端工作环境、长任务必须后台执行、自进化只修改声明式 skill 和文档。以下待验证项在已确认的远程执行方案下展开，不再以手机承担完整 Agent 运行环境为前提。

- Agent：首个 demo 通过 Pi SDK 集成现有 LiteLLM；具体版本与工具边界见 [demo 技术说明](demo.md)。后续完整工作环境及自定义能力仍待验证。
- 会话：支持多个通用会话，通过工具按需查询和操作共享模块与事项；需设计会话上下文、共享偏好与并发修改方式。
- 工具：向 Agent 提供事项和卡片管理、模块查询、自定义模块管理及定时任务能力。
- 服务端沙箱：必须支持代码运行、按需安装工具、文件操作与对外连接；SSH 连接远程电脑并开展开发是用户给出的代表场景。需核验 Linux 执行环境、包安装能力、资源限制和宿主机隔离，不能仅以固定工具调用或只能运行少量脚本的环境替代该需求。
- 远程任务：SSH 工具应可由 Agent 在工作环境中按需安装和使用，不预先内置 Qortex 专用功能。凭证传递、存储与日志处理方式待设计；产品场景不是当前会话的远程操作授权。
- 自适应调度：依据用户反馈持续调整计划、提醒与优先级；演化产物限定为声明式 skill 和文档。反馈记录、效果评估、文档版本和回退方式待设计，不把固定排序规则当作已满足需求。用户要求创建功能或执行任务时的代码编写、工具安装应与自进化分开记录。
- 自定义模块：需要动态加载、停用、故障隔离与本地版本回退；需验证可执行代码与界面扩展方式，以及代码版本与模块数据的兼容性，不能预先假定可以动态加载任意原生代码。
- 自动记账：拟通过 Android 无障碍能力检测支付宝、微信付款页面并截图交给模型；采用通知进入预填确认页面的交互，页面识别、截图可用性及目标设备兼容性待验证。已确认账目的修改权限须在实际写入入口执行，不能仅靠提示词约束。
- 记账去重：用户提出 pHash 等图像指纹作为候选方法；需结合交易内容验证重复识别与相似页面的区分，不把图像相似度直接当成交易身份。确认、取消和未识别成功时如何更新去重记录，需随产品规则确定。
- 健康：用户提出接入小米手环 SDK，目前手环型号未知，配套 App 据用户描述为“小米健康”。开放 SDK 的存在、适用设备、可用数据和接入条件均需核验，不能视为已确认可接入。
- 后台运行：已设本地提醒与依赖模型的任务需分开处理，支持离线查看、联网续处理及提醒补发去重；锁屏调度精度和系统重启后的行为需在目标设备验证。
- 兼容性与性能：目标设备为用户提供的索尼 XQ-AT72、Android 11；需核验依赖兼容性，并评估手机页面扫描、截图、同步与界面呈现的内存、响应速度和耗电，另行验证服务端执行与模块加载的资源开销，尚未实测。
- 消息与投资：远程消息服务、金融数据 skill 和投研地图 skill 均属后续接入方向，当前投资模块仅需支持对话记录投资想法；不提前要求这些服务接口。远程消息服务本身不在本项目中实现。
- 音视频：用途尚未明确，暂不选择处理库。
- 操作记录：首个 demo 使用 PostgreSQL 保存用户操作及 Agent 写入回执，手机离线操作通过待提交队列同步；后续完整检索、导出和手动清理方式仍待设计。

首个 demo 的具体依赖、原生提醒、存储与接口见[技术说明](demo.md)，验证结论见[验证记录](verification.md)。本页其余待验证项仍属于后续产品能力，不能用 demo 的简化范围替代。
