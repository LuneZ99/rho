# 产品需求

本文记录已确认的产品范围和待讨论的问题，供用户阅读、评审与修改。当前处于需求讨论阶段，尚未启动功能实现。

## 产品目标与范围

rho 帮助用户按不同生活领域管理信息和事项。用户通过对话交给它信息、创建功能或处理事情；打开 App 时，首页卡片展示当前值得关注的内容，并提供处理入口。

- 暂时只做 Android 手机 App。
- 首先供用户本人使用，目标手机为索尼 XQ-AT72，Android 11。需要重视老手机上的流畅度、内存占用和耗电，具体体验标准待细化。
- 首批优先实现健康、记账和投资；消息模块保留为后续方向。
- 尽量自动获取信息；无法自动获取的信息，由用户通过对话分享进来。
- 当前不向手机上的其他 App 发送消息或代为操作；需要提醒用户时，可以发送通知。用户另行指定远程电脑与任务时，希望 Agent 能在该电脑上开展工作，见[共享工作空间](#共享工作空间)。
- 下述内容是产品方向和已明确的行为，不代表所有功能都已确定进入首版。

## 模块与事项

模块用于管理一类事情，每个模块包含一系列事项，也可以有专属功能。

- 内置模块长期提供，其增删通过 App 开发完成，不能通过日常对话增删。
- 自定义模块可以通过对话创建、查询、修改和归档；归档与彻底删除的区别仍待明确。
- 用户可以通过对话创建、查询、修改和删除事项。
- 事项具有通用能力，不同模块可以增加专属信息和操作。具体通用字段尚未确定。
- 每个模块有适合自身内容的卡片样式。

### 内置模块构想

| 模块 | 希望完成的事情 |
| --- | --- |
| 记账 | 自动发现支付宝或微信付款页面，由 AI 识别后发送通知，用户进入确认页面修改或确认，再保存为记账记录。 |
| 健康 | 围绕腰围、睡眠和运动能力提供记录与计划，记录身高体重、服药及护肤情况，并探索接入小米手环数据。 |
| 消息 | 从已接入的远程服务获取社交媒体消息摘要，提取重要事项，并保留聊天总结供以后查询。远程消息服务本身不在本项目中实现。 |
| 投资 | 首先支持通过对话记录投资想法；关注范围为一个 A 股股票账户。持仓截图和投研服务等后续能力暂不展开。 |

各模块的信息来源和具体功能范围将在设计时细化。

### 自动记账

- 自动识别付款页面上的金额和消费详情，并从预先定义的消费类型中判断所属类别。
- 识别后发送通知，用户点击后进入确认页面；金额、消费类型和消费详情等信息预先填好，用户只需按需修改并确认保存。
- 同一付款页面被重复看到时，应跳过已处理内容，避免重复记账；不同交易不能仅因页面相似就被当成同一笔。
- 第一版不处理退款和转账。
- 已有账目不能由 Agent 自主更正或删除；用户需要审查时，会在对话中提出，再按其指令处理。
- 消费类型清单、关闭确认页面后的处理与不确定识别结果的呈现方式，留待具体交互设计。

### 健康

- 用户希望控制腰围、改善睡眠、提高运动能力；用户自述当前运动能力明显低于平均水平，计划需要考虑其实际起点。
- 需要记录身高、体重、服药情况和护肤情况。
- 希望结合身体状态讨论个性化健康管理计划与运动建议；具体建议时间和记录方式待设计。
- 用户已有小米手环，当前使用的配套 App 据用户描述为“小米健康”；手环具体型号尚未确认，自动读取数据的可行性也尚未核实。

### 投资

当前只明确通过对话记录投资想法，不要求此阶段完成持仓管理、外部报告接入或自动复盘。账户范围先限定为一个 A 股股票账户。

同花顺持仓截图、盘中建议和每日复盘保留为后续构想，当前不讨论局部截图如何更新持仓等细节。未来拟通过“金融数据 skill”和“投研地图 skill”接入相关能力，具体接入方式另行设计。

### 自定义模块

用户希望通过对话做出新的小功能，包括所需的信息、处理规则和呈现方式，而不只是给固定表单增加字段。

自定义功能应能在使用过程中加入或停用；创建后可以直接启用，无需额外确认。一个自定义功能出错时，停用该功能并通知用户，不应影响其他模块和 App 的正常使用。

本地保留功能版本，支持用户一键回退；具体保留数量和数据如何随版本恢复待设计，不默认自动回退。用户认为某个功能值得长期保留时，会在项目开发过程中将其重构为内置模块，日常对话不直接完成这一转换。

## 页面与对话入口

- 提供三个主要入口：首页、对话、模块。
- 首页展示需要关注和处理的卡片；模块入口用于查看各模块及其记录。
- 可以建立多个通用对话，不按模块划分专属聊天；每个对话都能按需查询和处理不同模块及事项。
- 从卡片进入详细处理时，将卡片的相关信息带入对话。进入已有对话还是新建对话，以及多个对话如何共享长期偏好，留待设计。

## 首页卡片

- 首页展示根据事项生成的卡片，并按重要性排序。视觉方向参考用户提到的钉钉 ONE，具体布局待设计。
- AI 按模块的卡片样式生成内容；排序随用户反馈与日常节奏调整，见[适应用户节奏](#适应用户节奏)。
- 事项持续保存，卡片表示该事项在某个时刻值得关注。同一事项可在不同阶段产生不同提示。
- 用户可以忽略卡片、点击预设按钮直接处理，或进入详细处理。
- 预设按钮对应事项允许的操作或属性选择。
- 详细处理会把该卡片带入 Agent 对话，继续通过对话处理。
- 忽略卡片不等于删除或完成事项。事项需要记住卡片被忽略的情况。
- 忽略时可以表达降低优先级或临时推迟的意图；下次生成和排序时应考虑这些选择。具体选项与推迟时长待定。

## 对话与自动处理

- Agent 可以直接创建事项和提醒，无需每次先要求用户确认；事项和提醒可以有对应卡片。
- Agent 可管理事项、卡片、自定义模块和定时任务，并查询模块。
- 对通用事项，Agent 可以直接修改时间、取消提醒、标记完成或删除，无需逐项确认；出现实际问题后再增加针对性约束。记账遵循[自动记账](#自动记账)中的专门确认与修改规则。
- 有新信息、相关事件发生或到达计划时间时，自动处理新增或变化的内容，生成或重新排列卡片，并执行定时任务。
- 锁屏后需要继续运行计划任务和发送通知。
- 手机断网时，仍可查看已经保存的事项、卡片和记录，已经设好的提醒继续生效；手机上尚未提交的 AI 请求等待联网。已被服务端确认接收的任务独立继续；需要手机新数据或用户回答的步骤等待，不把手机断网等同于所有服务断网。
- 错过的提醒可以补发；多条积压提醒如何合并、是否有过期时限尚未确定。已经正常送达的提醒不能因网络恢复而再次发送。
- 锁屏提醒应尽量准时，允许稍许偏差，以成熟提醒类 App 的使用体验为参考；具体可接受延迟尚未量化。

### 适应用户节奏

所有定时任务和计划任务都由 Agent 管理。主动整理、建议、卡片优先级与提醒安排应根据实际使用逐步调整，不预先写死一套适用于所有情况的频率或优先级规则。

如果某件事经常与用户其他安排冲突，或者用户经常没有时间、没有兴趣去做，其优先级应降低。用户的处理、忽略、推迟和对话反馈，需要成为后续调整的依据。

自我改进仅限声明式技能和文档，即记录“什么情况下怎样做”的说明与经验，参考 Hermes 的思路。不会通过自我改进修改 App 核心程序或训练模型。具体如何评价效果、展示调整以及撤销调整，留待设计。自适应安排不代表可以自行取消已经明确的产品要求，例如记账确认和已有账目的修改限制。

这与用户明确要求创建自定义功能、安装工具或编写任务代码是不同的行为：这些能力仍保留，但不应借“自我改进”自行扩展核心程序的修改范围。

## 共享工作空间

Agent 需要能在受限工作空间运行代码，并根据任务安装所需工具、管理工作文件、连接外部服务。用户期待具备能实际完成任务的完整工作环境，不局限于 App 预制的几个工具。运行的代码不能任意访问或修改 Android 系统。

已确定采用手机 App 配合自有服务端：Agent 与完整共享工作环境运行在服务端，业务主记录也保存在服务端；手机负责操作入口、设备采集、离线副本和本地提醒。首版无需选择本地或云端对话。部署安排见[运行位置决策](engineering/agent-runtime-decision.md)。

用户给出的代表场景是：临时几天，通过对话提供连接信息和凭证，让 Agent 连接另一台电脑，进行 Qortex 项目的开发。相关工具由 Agent 按需安装和使用，App 不需要预先内置一个专门的远程开发模块。该场景用于定义产品能力，不代表当前已授权连接任何电脑或修改其他项目。

多个对话共用同一套工作环境，包括已安装工具和工作文件；共用环境不意味着将所有聊天原文自动拼进每次对话。

离开 App、切换应用或锁屏后，长任务仍需继续执行，完成或需要用户回答时通知。中断恢复时，需要先检查已有进度再继续。具体保证条件、允许访问的数据与设备能力，以及临时任务结束后的保留方式，仍待设计。远程任务场景是否需要形成独立模块，也尚未确定。

## 操作记录

记录用户在 rho 中的全部操作，供以后回看和分析，改进 AI 的提示与处理流程。

操作记录长期保存，不按时间自动清理。如果本地占用过大，可以考虑保存到服务器；服务器存储尚未确定实施方案，也尚未启用。

是否同时记录 Agent 的决策和动作、是否保留截图及对话原文，以及如何查看、导出和手动删除，仍待明确。“长期保存”不自动扩展记录内容的范围；“全部操作”是否还包括 rho 自动观察到的外部页面事件，也需确认。

## 尚待细化

- Agent 声明式技能与文档改进的效果判断和调整记录。
- 临时远程任务的结束与保留方式。
- 记账消费类型、不确定结果和关闭确认页面后的处理。
- 自定义功能版本保留与数据恢复规则。
- 提醒积压处理与可接受延迟。
- 小米手环的具体型号与所需数据。
- 健康记录与计划的日常使用方式。
- 操作记录的内容范围、服务器存储及导出方式。
- 音视频处理的具体场景；此前提出了能力方向，尚未定义用途。
- 各功能的完整验收场景。

## 已明确的验收场景

以下场景用于后续实现验证，尚未执行，也不代表完整验收清单。

- 自动识别付款页面后发送通知，点击通知可查看预填信息并修改；用户确认前不形成正式账目，确认后保存金额、消费类型与详情。
- 用户未提出修改要求时，Agent 不自行更正或删除已有账目。
- 再次看到已经处理的同一付款页面，不重复生成账目；两笔不同交易即使金额相同，也不应因此被合并。
- 忽略卡片后，原事项仍然存在，并保存忽略选择，供后续生成和排序使用。
- 自定义功能出错后，该功能被停用，用户收到通知，其他模块仍可使用；用户可以选择回退到本地保留的版本。
- 手机断网后，已有事项、卡片和记录仍可查看，已设提醒继续生效；手机上尚未提交的 AI 请求在联网后处理。服务端已确认接收的任务继续执行，需要手机新数据或用户回答时等待。
- 联网后允许补发错过的提醒，不重复发送已正常送达的提醒。
- 用户可创建多个通用对话，并在任一对话中按需查询和处理不同模块的事项，无需切换到模块专属聊天。
- 对经常因时间冲突、无时间或无兴趣被搁置的事项，后续安排应体现优先级下降；具体评价方式待设计。
- 多个对话可使用同一工作环境中已安装的工具与文件。
- 自我改进产生声明式技能或文档的变化，不自行修改 App 核心程序。
